# Final Check PRD v0.1.0

## 1. 产品概述

### 1.1 产品名称

**Final Check**

中文名暂不确定，后续补充。

### 1.2 产品定位

Final Check 是一款面向合同版本往返、修订比对和格式整理场景的本地桌面工具。

核心目标是帮助用户快速完成：

1. 标准合同模板管理；
2. 合同多版本管理；
3. 我方版本与对方版本的往返管理；
4. 修订版与标准模板、我方基准版本的差异比对；
5. 文本修改、Word 修订、批注、格式修改和表格修改识别；
6. 重复修改自动规则归并；
7. 文字版修改说明和 Excel 修改清单生成；
8. 按原模板格式一键恢复修订版合同格式；
9. 保存完整合同版本和比对历史；
10. 支持备份、恢复和跨设备迁移。

Final Check 不承担合同法律风险分析，不提供 AI 法律判断或自动审查结论。

# 2. 产品设计原则

## 2.1 本地优先

MVP 核心功能必须在没有 AI API、没有网络的情况下正常使用。

核心本地能力包括：

- DOCX 解析
- 模板匹配
- 文本比对
- 修订读取
- 批注读取
- 格式差异识别
- 表格差异识别
- 规则归并
- 格式恢复
- 历史管理
- 修改说明生成
- Excel 修改清单生成

AI 仅作为未来增强能力。

---

## 2.2 原始文件不主动修改

软件默认：

- 不复制用户原始 DOCX；
- 只记录原文件路径；
- 不主动修改用户原文件；
- 不强制将原文件设置为只读。

所有格式恢复、导出和结果文件均生成独立文件。

---

## 2.3 历史不可覆盖

任何重新比对操作均生成新的独立比对记录。

以下操作不能自动覆盖旧记录：

- 更换标准模板
- 切换我方基准版本
- 原文件被修改
- 外部编辑格式恢复版
- 手动重新比对
- 使用新模板重新比对
- 重新执行格式恢复

---

## 2.4 修改事实与后续处理分离

即使用户已经执行格式恢复：

> 对方原本修改过格式

这一事实仍应保留在修改清单中。

例如：

> 字体：宋体 → 仿宋  
> 状态：已恢复

不得因恢复成功而删除原始格式修改记录。

# 4. 模板中心

## 4.1 模板基础信息

每个合同模板至少包含：

- 模板名称
- 合同类型
- 模板版本
- 是否当前启用
- 文件路径
- 创建时间
- 更新时间
- 标签
- 备注

---

## 4.2 模板版本

同一模板允许存在多个历史版本。

例如：

- v1.0
- v1.1
- v1.2
- v2.0

新增版本时：

- 不覆盖旧版本；
- 自动建议下一个版本号；
- 用户可手动修改版本号；
- 用户可将任一版本设置为当前启用版本。

若版本号重复，应提示用户确认或重新填写。

---

## 4.3 当前启用版本

当前启用版本：

- 在新项目创建时优先推荐；
- 在自动匹配时拥有更高优先级；
- 但历史模板版本仍参与匹配。

---

## 4.4 模板删除

允许删除模板或模板版本。

删除前必须展示：

- 当前引用该模板的项目；
- 当前引用该模板的历史比对记录。

用户确认删除后：

- 模板中心不再展示或用于新比对；
- 已有历史比对记录继续保留；
- 依赖历史结构化快照进行查看。

不得级联删除历史项目。

---

# 5. 模板自动匹配

## 5.1 匹配因素

可综合使用：

- 文件名
- 合同标题
- 条款标题
- 条款结构
- 正文相似度
- 表格结构
- 模板历史特征

---

## 5.2 候选模板

自动匹配后显示：

> 匹配度最高的前 3 个模板

每项显示：

- 模板名称
- 版本号
- 当前版本 / 历史版本
- 匹配度

---

## 5.3 用户确认

软件不能因为匹配度较高自动开始比对。

必须：

1. 显示推荐模板；
2. 用户确认；
3. 再进入比对。

前三项都不合适时，提供：

> 手动选择其他模板

---

## 5.4 已绑定项目

项目已经绑定标准模板后：

默认直接使用该模板。

用户仍可：

- 重新执行自动匹配；
- 手动更换模板。

更换模板默认只影响后续比对。

历史版本可使用新模板重新生成新的比对记录。

---

# 6. 合同项目

## 6.1 项目字段

每个项目至少保存：

- 项目名称
- 对手方名称
- 合同类型
- 当前模板
- 模板版本
- 所属文件夹
- 标签
- 项目状态
- 创建时间
- 更新时间
- 当前我方基准版本

---

## 6.2 项目名称自动建议

Project / Template / Version Management v0 先提供基于所选模板标题与用户明确填写对方的轻量建议，不引入 NLP，也不将未验证的正文/文件名推断当作事实。建议由用户核对后保存；未来可靠信息抽取需独立验证。

软件根据：

1. 合同标题
2. 对手方名称
3. 文件名

自动建议项目名称。

用户确认或修改后保存。

项目后续可重命名。

项目名称变化不得自动修改 DOCX 文件名。

---

## 6.3 对手方识别

本阶段无法可靠识别时留空，由用户明确填写；不猜测对方，也不得用文件名、作者或路径推断版本角色。

优先从正文识别。

若无法可靠识别：

结合文件名给出建议。

最终由用户确认。

记录识别来源：

- 正文
- 文件名
- 用户手动

---

## 6.4 合同类型

优先根据当前绑定模板确定。

用户可手动修改。

修改合同类型不得自动更换标准模板。

# 8. 项目状态

项目状态至少区分：

- 正常
- 已归档
- 回收站

---

## 8.1 正常项目

默认进入正常项目页。

按：

> 最近更新时间

倒序展示。

支持筛选：

- 项目名称
- 模板类型
- 更新时间
- 文件夹
- 标签

---

## 8.2 归档

参考 In Line 的项目管理逻辑。

归档适用于：

> 已结束，但仍需保留的合同项目。

归档后：

- 从正常项目隐藏；
- 保留全部数据；
- 保留版本；
- 保留快照；
- 保留比对记录；
- 可搜索；
- 可恢复。

---

## 8.3 回收站

删除项目时：

先进入回收站。

回收站默认永久保留。

支持：

- 恢复
- 彻底删除
- 一键清空回收站

彻底删除后才清除：

- 项目数据
- 历史比对
- 快照
- 修改状态
- 格式恢复记录

原始 DOCX 不受影响。

# 9. 合同版本模型

## 9.1 版本角色

每个合同文件上传时，由用户明确指定：

- 我方版本
- 对方版本

软件不依赖：

- 文件名
- 修订作者
- AI

自动决定版本角色。

---

## 9.2 轮次

每个合同项目支持多轮谈判。

上传文件时选择：

- 加入当前轮次
- 新建下一轮

---

## 9.3 同轮多版本

每一轮均允许：

- 多个我方版本
- 多个对方版本

例如：

第 1 轮：

- 对方版本 A
- 对方版本 B
- 我方版本 A
- 我方版本 B
- 我方版本 C

---

## 9.4 当前基准版本

同一轮多个我方版本中，可指定一个：

> 当前基准版本

仅我方版本可以设为基准。

操作入口：

- 版本时间线节点
- 版本详情页

---

## 9.5 新我方版本

上传完成后提示：

> 是否设为当前基准？

默认：

> 否

不得自动替换现有基准版本。

# 11. 文件导入

## 11.1 导入方式

支持：

- 点击选择文件
- 拖拽文件

---

## 11.2 左右分区

导入界面划分为：

左侧：

> 我方版本

右侧：

> 对方版本

文件拖入对应区域后自动确定角色。

点击右侧选择文件自动视为对方。

---

## 11.3 批量导入

左右两侧均支持多个文件。

一次导入可同时包含：

- 多个我方版本
- 多个对方版本

导入前进入统一确认列表。

- 删除误选文件
- 设置轮次
- 加入当前轮次
- 新建下一轮

---

## 11.4 批量导入行为

批量导入：

> 只保存文件和版本信息。

不在导入过程中：

- 设置比对方式
- 自动执行比对

后续从版本节点手动发起。

---

## 11.5 重复文件

通过哈希检测。

检测到当前项目已有相同文件时：

提示：

- 跳过
- 仍然导入

仍然导入时标记：

> 与已有版本内容一致

---

# 12. 比对方式

## 12.0 Quick Compare / 独立比对入口

“快速比对”继续提供左侧基准版本、右侧当前版本，每侧选择或拖入一个 DOCX，不要求建立项目、模板或轮次。Project / Template / Version Management v0 另建立模板中心、合同项目、明确我方/对方的批量版本与轮次、当前我方基准和独立历史工作流；两种入口复用同一正式 Comparison Engine、结果与审阅 UI、冻结历史和原始路径/hash 规则。批量导入不自动比对；项目比对明确选择已导入的冻结版本与模板当前/历史或当前我方基准，不重新读取已变化的原文件。范围及最终安装验收以相应 task 为准。

## 12.1 与标准模板比对

用于查看：

> 当前合同相对公司标准模板的累计变化。

---

## 12.2 与当前基准版本比对

用于查看：

> 对方相对于我方最新可接受版本又修改了什么。

---

## 12.3 用户选择

单文件对方版本上传完成后进入：

> 选择比对方式

提供：

- 与当前基准版本比对
- 与标准模板比对

软件记住用户上一次选择。

下一次默认预选，但仍由用户确认。

---

# 14. 文档差异来源

必须区分两类修改。

## 14.1 Word 原生修订

读取 DOCX 内已有：

- 插入
- 删除
- 修订作者
- 修订时间
- 批注
- 格式修订

---

## 14.2 实际版本差异

即使对方：

- 接受全部修订；
- 关闭修订模式；
- 直接编辑；
- 删除修订记录；

仍需通过：

> 基准文件 VS 当前文件

独立执行实际内容比对。

---

## 14.3 结果合并

两类数据最终合并为：

> 实际修改清单

但底层应保留来源信息。

---

# 15. 文本比对

先建立：

> 条款 / 段落级对应

再执行：

> 词语 / 字符级差异

例如：

原：

> 付款期限30日

新：

> 付款期限60日

仅突出：

> 30日 → 60日

若整段重写，则允许退化到段落级。

---

# 16. 条款移动

尽量识别：

> 条款移动

而不是：

> 删除 + 新增

保存：

- 原位置
- 新位置
- 原条款号
- 新条款号
- 标题

若同时发生内容修改：

同时标记：

- 条款移动
- 内容修改

---

# 17. 修改位置

优先显示：

> 条款号 / 条款标题 + 页码

若无法识别：

> 页码 + 段落位置

点击修改项后：

直接定位到对应文档位置。

---

# 18. 批注

批注优先关联到对应修改项。

修改项中展示：

- 批注内容
- 批注人
- 时间

同时提供：

> 独立批注视图

无法关联的批注单独保留。

# 45. 存储空间管理

提供独立页面，并在“设置 → 存储”提供数据位置管理入口。以下为 v0.1.0 正式产品要求；需求落档不代表设置页、路径迁移或安装向导已经实现。

## 45.1 存储统计与位置操作

显示：

- 总数据占用
- 项目数据
- Database
- Snapshot / 快照
- Comparison / 历史比对
- Format Restore records / 格式恢复记录
- Working Copy
- Backup / 内部备份与恢复
- Cache
- Logs / Temp

“设置 → 存储”必须显示当前数据位置、当前占用空间，并提供“打开数据文件夹”“更改数据位置”。统计针对当前实际 DataRoot；迁移成功后立即刷新，无需重启。SQLite 内 Snapshot / Comparison / 恢复 payload 的逻辑占用须注明包含于 Database，不重复累加到物理总占用。

清理前必须明确说明影响范围。

## 45.2 安装目录与数据目录独立

> Application install location and application data location are independent concepts.
>
> User data must never be stored inside the replaceable application installation directory.

SQLite、Snapshot、Comparison、格式恢复记录、Working Copy、内部 backup / recovery、应用缓存、日志/临时文件、可迁移设置及应用运行数据统一由独立 DataRoot 管理，不得放在应用安装目录或可替换的 current 中。

新用户默认数据目录可以为 `%LocalAppData%\FinalCheck\Data`；用户可改为 `D:\FinalCheckData` 等本机可写的固定磁盘绝对目录。已有旧 AppData 数据须识别并兼容，不得因为新默认路径创建空库而隐藏旧历史。

原始用户 DOCX 仍只记录原路径，不复制到 DataRoot。手动导出的 DOCX / Excel / 修改说明继续遵循第 48–50 章的输出路径与同名文件规则；更改 DataRoot 不改变原始或导出文件位置。

## 45.3 启动定位

允许在 `%LocalAppData%\FinalCheck\bootstrap.json` 保留小型启动配置，仅记录当前 DataRoot、必要 storage schema / version 和最小启动恢复信息。实际业务数据位于 DataRoot；不得以目标 SQLite 内设置作为 DataRoot 的唯一来源。配置位置通过平台抽象提供，为 macOS 保留兼容性。

配置损坏、目录不可达或既有数据库缺失时明确提示恢复，不静默回退默认目录创建新数据库。

## 45.4 非破坏性更改数据位置

正式流程：选择新目录 → 验证路径/写权限/空间 → 阻止新数据库及托管文件写入并等待当前操作结束 → 将完整一致性数据复制到目标临时目录 → 验证数据库、关键文件、必要 SHA-256 / 数量 / 大小 → 使用新目录重新打开数据层并验证完整性 → 原子更新 bootstrap → 正式切换。

- 迁移需要 operation record / 日志，记录阶段、校验与失败原因，支持恢复和重试。
- 禁止直接剪切、删除原数据或覆盖目标已有另一套数据；不能只复制活动 SQLite 的 .db 而遗漏 WAL 中已提交数据。
- 未成功切换前任何失败保持旧 DataRoot 生效、旧数据完整，清楚显示失败阶段和原因并允许重试。提交不确定/崩溃时依据 durable locator 与 operation record 恢复，禁止猜测双写或静默退回旧库形成分叉；具体提交边界见 storage architecture。
- 成功后新路径立即生效，UI 与统计无需重启；旧路径数据默认保留，后续只有用户明确选择并确认影响范围才能清理，不自动删除。
- 托管 Working Copy / backup 引用随迁移保持可用，Snapshot、Comparison 和格式恢复历史/Undo 关系不丢失，不改写原始 DOCX 或历史文档内容。

## 45.5 首阶段外部存储政策

v0.1.0 首阶段正式支持 Windows 本机固定磁盘、用户有读写权限的绝对目录。NAS / SMB / 映射网络盘、可移动磁盘、已识别 OneDrive 等同步目录不作为主 DataRoot 支持，应阻止并解释风险；SQLite 主库未经可靠性验证不得宣称支持网络盘。无法充分识别的同步工具风险明确披露，不能因为“可写”就视为可靠支持。

实施与验收依据：[storage-and-paths.md](../architecture/storage-and-paths.md)。

Storage Foundation v0 已落地定位、旧库兼容、非破坏性迁移、内部 data session 热切换和占用统计基础服务，实际测试/平台/打包证据以 [任务文件](../tasks/storage-foundation-v0.md) 为准。本基础阶段不代表“设置 → 存储”正式 UI 或安装目录 Wizard 已完成；不改变本章产品要求与导出规则。

# 65. AI 后续定位

AI API 后续只用于：

> 修改项语义归并

例如：

- 第4.2条：30日 → 60日
- 附件一：账期30天 → 60天
- 第8条：付款期限延长

可归并为：

> 付款周期调整

AI 不得自动输出：

- 高风险
- 低风险
- 建议拒绝
- 建议接受
- 法律责任判断

---

# 66. 产品边界

Final Check 的核心定位最终确定为：

> 一款围绕合同模板、双方版本、多轮修订、修改整理和格式恢复构建的本地合同版本管理与比对工具。

它解决的是：

> “改了什么、哪里改了、怎么整理、格式怎么恢复、版本怎么追踪。”

而不是：

> “这个修改是否合法、风险多高、应该怎么谈。”

# 67. 后续统一项目标准

自 Final Check 起，后续新软件项目默认沿用以下基准，无需重复确认：

1. GitHub Actions 参考群聊拾遗；
2. Release 流程参考群聊拾遗；
3. 软件内更新逻辑参考群聊拾遗；
4. 下载进度、失败重试、正式版/测试版更新逻辑保持一致；
5. 数据备份恢复设计优先参考 In Line 已验证经验；
6. 归档、回收站等项目管理方式优先参考 In Line；
7. 已验证成熟能力优先复用，不重复设计。
