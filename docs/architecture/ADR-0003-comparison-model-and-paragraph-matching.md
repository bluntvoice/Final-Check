# ADR-0003：Comparison 结果模型与多信号段落匹配

- 状态：Accepted
- 日期：2026-09-10

## 背景

Comparison Engine 需要基于 `DocumentSnapshot` 输出可定位、可解释并可持久化的比较结果。按 Paragraph index 直接配对会在文档前部插入或删除段落后产生大量错误映射；只使用文本相似度又会在重复短段落和结构相近内容中制造不确定结果。

结果模型还需要被 Data 和未来 UI 使用，但 `FinalCheck.Comparison` 不应成为这些层的反向依赖来源。

## 决策

1. 将稳定、可序列化的 `ComparisonResult`、ChangeItem、NodeMapping、diagnostics 和 statistics 领域模型放入 `FinalCheck.Core.Comparisons`。
2. 将匹配、文字 Diff、格式 Diff、归并等算法接口和实现保留在 `FinalCheck.Comparison`。
3. 段落匹配采用分阶段、多信号策略：结构与规范文本精确匹配优先，之后使用标题/编号、文本、位置、样式和相邻上下文综合评分。
4. 使用位置窗口、Token 倒排索引和标题键缩减候选，并限制单段候选数量；不得用全部段落笛卡尔积作为正常匹配路径。
5. 每个映射保留数值分数、离散 confidence 和证据。低分或近似并列候选保持 Unmatched，并通过 diagnostics 暴露原因。
6. 所有候选排序和重复文本处理采用稳定顺序，保证同一输入结果可复现。

## 影响

- Data 可依赖 Core 中的稳定 payload 模型，无需引用算法程序集。
- UI 可在不了解匹配实现的情况下消费映射、修改项与诊断。
- 插入、删除和大范围位移不会仅因 index 偏移破坏后续段落映射。
- 重复短文本可能被保守地留下未匹配，或以中等可信度顺序配对；调用方可以识别而不会收到伪造的确定结果。
- 后续 schema 发生不兼容变化时必须提升版本并提供明确的兼容策略。

## 未采用方案

- 纯 index 匹配：无法应对插入、删除与移动。
- 纯文本阈值匹配：缺少结构和上下文证据，重复段落歧义较高。
- 全量段落两两比较：时间和内存复杂度不适合作为中型合同的默认路径。
- 将结果模型放在 Comparison 项目：会迫使 Data 或其他消费者依赖算法实现层。
